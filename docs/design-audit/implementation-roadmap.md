# Implementation roadmap

**Awaiting review. This plan authorises no redesign work by itself.** Each phase below is a future implementation slice. Accessibility and mobile checks are acceptance criteria in every phase, not a final clean-up pass.

Complexity is relative engineering effort: **S** local/low coupling; **M** several consumers with moderate behaviour risk; **L** cross-cutting state or many page families. Estimates assume the existing React/Tailwind/Supabase stack, no library replacement and available synthetic/staging fixtures. Device/user validation and unknown production edge cases can increase effort.

## Review gates and acceptance criteria

Before implementation, approve the proposed palette/type/shape/spacing, component contracts, mobile navigation hypothesis, templates, and staged scope. Discuss any requested library/router addition separately; none is necessary to write tokens and improve the existing primitives.

Before migrating the next page family, review one complete mobile staff slice (Members → Weekly Marks → member correction → safe return), one settings form/dialog and one portal view. Confirm that they share a design language without exposing different roles' data or flattening useful workflow differences.

A slice is done only when:

- Page/header/toolbar edges and typography match its approved template; no unintended arbitrary colour/radius/control variant is introduced.
- At 320px, primary tasks work without document overflow. Any intentionally scrollable data comparison is labelled, focusable, discoverable and has a usable mobile alternative or justified exception.
- Controls meet the product target and AA geometry/contrast requirements; keyboard focus remains visible; fields identify their object/date and errors.
- Saving, empty, loading, error and destructive paths are visible and understandable; a failure never masquerades as a genuine empty state.
- Existing domain and security tests relevant to the slice pass, and synthetic visual/interaction evidence is reviewed.

## Visual regression strategy

Use the existing Playwright Test dependency and CI rather than adding a second application testing stack. Keep the MCP capture harness for exploratory audit/reproduction; a future committed regression suite should use `expect(page).toHaveScreenshot` with explicit assertions before capture. The current `capture.py` is an evidence recorder, not a pass/fail regression gate: it records accessibility findings and capture errors without claiming the UI passes.

| Layer | Coverage and fixtures | Check |
| --- | --- | --- |
| Primitive contract | Buttons/fields/status badges/dialogs/alerts at base, focus, invalid, disabled, busy, long content and reduced motion; both section accents | Geometry, contrast pairs, keyboard/focus/labels plus stable clipped component images. Avoid tests that merely mirror class strings. |
| Page anatomy | All major staff/portal page families at seven widths; empty/populated/loading/error; long names, 20 squads boundary and roster sizes | Stable header/gutter/action/state geometry, document overflow and visual comparison. Explicitly exempt intended table overflow only at named containers. |
| Interaction states | Mobile More/menu, search/filter, add/edit, dirty/date-discard, past-date lock, validation, save/retry, archive/reset confirmation, export preparation | Assert correct state/label/focus, then capture; do not accept screenshots of skeletons or blank pages as passed tests. |
| Role/origin variants | Officer, captain/admin, ordinary boy, leader; Company/Junior; localhost vs supported hosted passkey/recovery | Fixture tests cover presentation; supported staging E2E covers actual auth/RLS/portal boundaries. Keep production-mutating smoke excluded. |
| Device/manual | iOS Safari/Android Chrome, software keyboards, text enlargement, short landscape, screen readers | Manual task checklist and retained synthetic evidence, outside the scope of pixel equality alone. |

Freeze time/timezone/locale, seed deterministic invented data, disable nonessential animation, await fonts and explicit UI readiness, block external/live backend requests in fixture runs, and use a pinned browser/OS/font environment. Capture clipped visible viewport states as well as purposeful full-page images; full-page screenshots place sticky/fixed UI relative to the original viewport.

Set a low documented pixel tolerance for rendering noise, not a large percentage that masks layout drift. Never automatically update baselines on CI failure. Review expected/actual/diff for each affected page family; token changes require reviewing both sections and portal/squad consumers. Keep baseline approval in PR review. Retain failure artifacts for a short period and ensure they contain synthetic data only.

Run unit/type/build and the relevant visual subsets on PRs; schedule the complete seven-width matrix when shared foundations change. Broaden to full device/manual review at milestones or when input/navigation semantics change. Avoid running live mutation suites merely to validate styling or documentation.

## Deliberately deferred

A new visual identity, new component library, paid design-service subscription, database changes, authentication changes and production deployment are outside this audit. PDF restyling/accessibility requires a separate output assessment, although its web dialog should use shared components. Dark mode is a future product decision, not an excuse to duplicate the initial theme implementation.
