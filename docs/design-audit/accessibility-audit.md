# Accessibility and usability audit

**Target: WCAG 2.2 AA.** This is a source and browser assessment, not a conformance certificate. The component harness is synthetic and automated axe results are incomplete without keyboard, assistive technology and real-device checks. See [README](README.md) for scope and evidence labels.

## Positive evidence

Add-member modal initially focuses Close, Shift+Tab reaches Add Boy, Escape closes, and focus returns to Add Boy. These behaviours were tested, so this audit does not claim focus trapping is completely absent. The issue is its stability and coverage.

Roster row actions have member-specific aria-labels. BoyForm and account password fields use labels, invalid states and linked error text. Password fields have relevant autocomplete attributes. Calendar/events use real buttons and textual dates/status; attendance is not colour-only. `BarChart` has an SVG title and per-bar titles; squad table has row headers and a focusable scroll wrapper. CompanyCalendar's event cards expose date, location and description as text. Global and weekly date-change guards protect unsaved marks; the synthetic validation check confirmed Stay retains the selected date.

Session archive retains a typed confirmation and PDF acknowledgement for an operation affecting both sections. Keep the stronger protection rather than flattening all confirmations to a generic dialog.

## Automated evidence and interpretation

Each `evidence/<case>.json` includes axe findings with selector, impact and failure explanation at each width. The audit ran axe with WCAG 2 A/AA, 2.1 A/AA and 2.2 AA tags; best-practice-only rules are not included. Missing dialog name was confirmed directly from DOM/source, independent of those tags. The script records all visible controls below the **product 44px** target as candidates; these records include disabled/background controls and are not an AA-failure count.

Representative evidence: [weekly](evidence/weekly.json), [member history](evidence/junior-member.json), [squad report](evidence/squad.json), [dashboard](evidence/dashboard.json), [interaction checks](evidence/interaction-checks.json). axe contrast findings on transparent/decorative items need human review, and browser font rasterisation is not a substitute for token contrast calculations. No total “accessibility score” is asserted.

## Required acceptance checks before approval of implementation

1. Keyboard: complete login, navigation, search/filter, add/edit, date change, marks save, confirmation and report flow; test Tab/Shift+Tab, Escape, focus return, async controls and busy/disabled changes. Verify no focus is hidden by the 80px header or bottom actions.
2. VoiceOver with iOS Safari and TalkBack with Android Chrome: landmarks, view-change announcement, named dialogs, member/date-associated fields, field errors, chart data alternatives and status messages.
3. Magnification: browser zoom/text enlargement, 320px reflow, landscape and short viewport heights; ensure primary tasks and controls remain visible. Real device checks must include the software keyboard.
4. Contrast: every text/surface pair, focus indicator, input boundary, selected/unselected state, disabled affordance, section/squad palette, chart legend and status badge. Normal text 4.5:1, qualifying large text 3:1, required non-text contrast 3:1.
5. Error prevention/recovery: offline, failed read/save, revoked portal access, stale event revision, failed passkey ceremony and protected session archive. Use controlled fixtures/staging accounts and preserve existing authorization checks.
6. Reduced motion and preferences: long loading, toast presentation, section hover movement, forced colours/high contrast and native form controls. Check that routine success does not interrupt reading.

PDF accessibility, tagging, reading order and printed contrast were not validated. `@react-pdf` document layouts require their own output review, including long names and page breaks; do not treat a web-modal scan as a PDF audit.
